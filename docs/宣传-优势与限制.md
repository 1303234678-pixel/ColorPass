# JYBridge 宣传文案包

> 用途：拍宣传视频时的**事实底稿 + 口播脚本 + 禁区**。
> 所有数字都有出处（代码 / 测试 / 实测报告），没有一处是估算。
> 竞品数据取自 2026-11-20 的公开资料与 GitHub API，写进视频前建议再核一次星数。

---

## 0. 一句话定位

**剪映剪辑，达芬奇调色，一条时间线来回走，回剪映还能接着剪。**

三个长度版本，按视频节奏挑：

| 长度 | 说法 |
|---|---|
| 超短句 | 剪映剪辑，达芬奇调色。 |
| 30 字 | 把你的剪映草稿整条送进达芬奇调色，调完再写回一份**还能继续剪**的草稿。 |
| 60 字 | 市面上的互转工具都在"搬工程"：导出 XML、渲染成片、新建草稿。它搬的是**可编辑结构 + 调色意图**：不落工程文件，LUT 回传，剪映里原有的变速、转场、蒙版、停用段一个不少。 |

**封面金句候选**

- 「不是把片子搬过去，是把时间线搬过去。」
- 「调色回来了，剪辑还在。」
- 「别人搬到成片，它搬回时间线。」

## 1. 它到底做什么（30 秒讲清）

面板只有三个按钮，全部嵌在达芬奇里（Workflow Integration 扩展，不装桌面宿主）：

```
① 送入达芬奇   → 按绝对帧号在达芬奇建一条时间线，逐段落轨
       ↓
   在达芬奇里调色（Resolve 原生，随便用节点/窗口/跟踪）
       ↓
② 写回剪映     → 每段导出 33³ LUT，克隆原草稿 + 只补一条 LUT 材质
       ↓
   剪映里得到一份新草稿：画面带调色，剪辑结构一处没动，可以继续剪
```

③ 锁定/解锁轨道 —— 防止调色时误碰剪辑点。

一条命令也能跑完整往返：`python -m jybridge.cli roundtrip`。

## 2. 市面格局（2026-11 实测口径）

先说结论：**这个需求被验证过了，但没人做到"往返 + 回剪映还能编辑"这一格。**

### 2.1 成规模的六类方案

| 方案 | 形态 | 剪映→达芬奇 | 达芬奇→剪映 | 高版本加密草稿怎么办 |
|---|---|---|---|---|
| **LMbox 彩虹桥**（免费） | 达芬奇扩展 + 必装桌面宿主 | 走 Resolve API 逐条落轨 | 调色回批：**渲染成片**写进草稿副本 | 绕开：让用户先在剪映「保存为预设」 |
| **春星开讲「剪映↔FCP 套底神器」** | 独立 Python 工具 | 导出 FCPXML | 靠剪映自带「导入工程」 | 扫运行时明文（**和本项目同一取巧点**） |
| **CutConvert**（付费网页） | 网页 | — | .drp/.drt → CapCut 工程目录 | 直接按 CapCut 格式写草稿 |
| **Free Forever Converter** | 网页 | 草稿 → FCPXML | — | 只读 project file |
| **「达芬奇-剪映桥接」插件**（付费） | 达芬奇面板 | — | 片段级：渲染成片 → 自动回批为新 Take | 不读草稿，只监听导出目录 |
| **开源草稿库生态**（pyJianYingDraft 等） | 库 / CLI / MCP | 不涉及达芬奇 | 只做"生成或修改草稿" | jy-draftc 调 `videoeditor.dll` 加解密 |

### 2.2 GitHub 上"剪映 + 达芬奇"精确搜索只有 4 个仓库

| 仓库 | 星 | 做到哪一步 |
|---|---|---|
| Ersiter/Jianying-CapCut2XML | 8 | 草稿 → FCP7 XML → 达芬奇 |
| chowjl/resolve-to-jianying | 6 | 达芬奇 → 剪映（单向，用 pyJianYingDraft 新建） |
| OnemoreUltra/jianying-to-davinci | 0 | 菜单脚本：DLL 解密 → API 逐段落轨。**只单向** |
| inkyhu/resolve-jianying-bridge | 0 | 双向，但一边新建、一边要求"保存为预设" |

### 2.3 有社区的都不做互转

| 项目 | 星 | 定位 |
|---|---|---|
| GuanYixuan/pyJianYingDraft | ≈4.9k | 草稿读/写库，上面两家都拿它当底座 |

## 3. 七个优势（每条都给证据）

### 优势 1 · 唯一做到"回剪映还能继续编辑"

- **别人**：重建或导出。彩虹桥回批是"按片段渲染的成片替换原素材"，成片进剪映就回到不可编辑；桥接插件回批是"拍平的成片 + 新 Take"，它自己都警告"可能与剪映成片叠加"。
- **你**：拿内存里读到的**完整明文草稿**当底，深拷贝，只给对应段 append 一条 LUT 材质。时间线一个字节都不动。
- **证据**：`jybridge/draftbuild.py` 的 `build_from_draft`；写回注释原文"时间线一个字节都不动，自然完全一致"。
- **视频里怎么让人相信**：写回后在剪映里**再拖一段、再删一段**，画面上的调色还在。这个镜头比任何参数都有说服力。

### 优势 2 · 不落任何工程文件，也不渲染成片

- **别人**：FCPXML / AAF / .drp / 交换文件夹 / 渲染成片，至少占一个。
- **你**：送入直接 `AppendToTimeline` 按绝对帧号落轨，不生成任何交换文件；调色回传导出的是 33³ cube（35,937 个采样点），再嵌进新草稿自己的 `Resources\JYBridge\`。
- **就算抠字眼也站得住**：cube 在 `%LOCALAPPDATA%\JYBridge\luts\` 只是一份工作副本，写回时复制进草稿，之后可被自动回收 —— 它不是工程文件，也不参与剪辑。
- **唯一的真例外**：变速段要 ffmpeg 预渲染成等长 ProRes（达芬奇脚本接口没有设置速度的入口）。

### 优势 3 · 调色以 LUT 回传，不是把画面烤死

- **别人**：回批 = 渲染一段新视频。调完色，剪辑信息就没了。
- **你**：`TimelineItem.ExportLUT(EXPORT_LUT_33PTCUBE)` 每段一个 cube，写进草稿的 effect 材质。剪映里那一段还是原素材 + 一个 LUT，**随时能改强度、能删、能换**。
- **这是"可编辑"的技术前提**，不是顺便。

### 优势 4 · 自带完整性断言，宁可拒绝写回

每次写回都逐项核对，任何一项不过就判失败，不给你一份"看起来成了"的坏草稿：

| 核对项 | 查什么 |
|---|---|
| LUT 落位 | 每段嵌入的 cube 与取回的那份是否同一个文件 |
| 时间线 | 每段入点 / 出点 / 时长逐段比 |
| 关键帧 | `common_keyframes` 整个 JSON 全等 |
| 转场 | 按 `(名字, 时长)` 多重集比（不是只数个数） |
| 蒙版 | 每段挂的蒙版引用逐段比 |
| 变速 | 倍率 + `speeds` 材质引用两处都比 |
| 停用状态 | `visible` 进结构指纹，被"复活"就报错 |
| 全轨结构 | 所有轨道类型（含独立特效轨/滤镜轨/文字轨）逐段比 |
| 复合片段 | 内部时间线逐字节比 |

- **别人**：一个校验都没有，全靠肉眼。
- **证据**：`jybridge/write.py` 的 `structure_index` / `structure_diff`；失败时 `rep["ok"]=False` 并写清是哪一项、哪一段。
- **口播**：「它宁可告诉你写回失败，也不会给你一份看着对、其实丢了东西的草稿。」

### 优势 5 · 明文读不到时，还有两条不靠内存的路

这是全网没人公开解决的那一段。

- **物理事实**：剪映打开草稿时把明文解密进内存，明文**会被回收**。实测一份没动过的草稿挂一小时后，内存里只剩 **166,976 字节**的残片（有 `"tracks":[`、没 `"materials"`、括号都不闭合）。
- **别人**：卡在"重开剪映再扫"这一步。春星开讲那套工具的原话就是"必须先打开剪映、必须加载了草稿，扫不到就什么都没有"。
- **你**：三级回退，前两级都是**秒级文件操作**。
  1. 本地缓存（磁盘指纹：密文载荷字节数 + 最后编辑时间，**完全一致**才用）
  2. 剪映载入备份 `.backup\*.load.bak`（写回的草稿是明文写入，备份也是明文）
  3. 进程内存扫描（体积对账，容差 320 B + 0.5%）
- **实测**：`cli check` 从 25 秒失败变成 **0.78 秒成功**（`plain_source=缓存`）。

### 优势 6 · 保真清单是"逐项承诺"，不是"大概齐"

竞品里带得最多的是 CutConvert（✅变速 / ✅主轨转场 / ❌特效滤镜蒙版）和 Free Forever（✅速度/淡入淡出/主轨转场/❌特效）。

**这一项必须分两列说，混着说会被抓。** 「达芬奇里看得到」和「写回剪映还剩什么」是两件事：

| 元素 | 达芬奇里 | 写回剪映 |
|---|---|---|
| 剪辑点 / 轨层 | 精确到帧 | 原样 |
| 变速 | 真变速（bake 重采样，帧序与剪映一致） | 原样（含曲线） |
| 转场 | 近似为硬切，位置与总长不偏 | 原样（真的转场还在） |
| 关键帧 / 入场出场动画 | 不带 | 原样 |
| 蒙版（含蒙版关键帧） | 不带 | 原样 |
| 停用片段 | 保留为**禁用片段**（灰的、位置不动） | 原样 |
| 复合片段 | 用内部素材重新合成 | 原样（含内部装饰） |
| 文字 / 贴纸 / 滤镜 / 特效 | 不带 | 原样 |
| 画面变换（缩放/位移/旋转） | 不带（按原素材铺满） | 原样 |

- 写回成功后，面板直接显示「原样保留：变速 2 段 · 转场 5 个 · 画中画 1 轨」。
- **这张表敢公开，是因为写回有 9 类断言逐段核对**（见优势 4）：不是嘴上说保留，是克隆完再逐段比一遍。

**停用片段**可以单独讲：剪映里 `visible:false` 的段仍然占着时间线。跳过的工具会让它在达芬奇里"复活"或多出一块黑场；本工具照样占位，落轨后调 `SetClipEnabled(False)`，达芬奇里就是灰的、位置不动、随时可再启用。

### 优势 7 · 工程性：轻到可以随手装

| 指标 | 数值 |
|---|---|
| 生产代码 | 约 7,400 行（`jybridge` 14 个模块 + `app` 五个文件） |
| 整个工程 | 源码 564 KB，含测试的目录 1.3 MB |
| 自测 | **308 个测试**，不依赖达芬奇、不依赖剪映、不动真实草稿 |
| 静态检查 | ruff + vulture 全绿 |
| 缓存治理 | 四道闸（活动草稿永不动 / 孤儿直接收 / 超期超量 / 600 MB 兜底） |
| 面板显示口径 | 只报**真能删掉的量**，删不掉的不显示，无可清项按钮直接灰 |

> 对比：这个项目原本是个 485 MB 的"独立调色工作站"，砍到只留互通之后，源码只有 564 KB。**"轻"本身也是卖点**。

## 5. 限制清单（诚实版，拍视频时不要藏）

分五类。**每条都写清"你会遇到什么"，因为限制讲得越准，可信度越高。**

### A. 平台与环境

| 限制 | 你会遇到什么 |
|---|---|
| 仅 Windows（当前实现） | 依赖 `%LOCALAPPDATA%` 下的剪映草稿目录，以及 `OpenProcess` + `ReadProcessMemory` 扫进程内存。macOS 上剪映同样加密草稿，但这套读取代码是 Win32 的 |
| 剪映必须开着、且目标草稿确实打开 | 目录里要有新鲜的 `.locked`。没打开就点 ①，会直接停，一个字不写 |
| 达芬奇必须开着 | 停在项目管理器时会自动新建一个空白工程 |
| 达芬奇工程里不能有别人的时间线 | 有就拒绝送入（怕弄乱你已有的工程）。只有本工具建的 `JY · …` 不算阻塞 |
| 较早的 Resolve（没有 `SetClipEnabled` 的版本） | 停用片段在达芬奇里会出画面（报告里标 `disabled_unsupported`，不判整次失败） |

### B. 剪映侧的机制性限制（不是 bug）

| 限制 | 你会遇到什么 |
|---|---|
| **改过草稿要重开** | 打开草稿、编辑保存之后点 ①，会弹"请重开草稿"。因为内存里那份明文是打开那一刻的版本，`Ctrl+S` 和"切走再切回"都无效 |
| **明文会被回收** | 挂久了（实测约 1 小时）内存里只剩残片，与是否编辑无关 |
| **首次可能仍需重开一次** | 三个条件同时成立时：从没成功读过这份草稿 + 已经打开很久 + 不是本工具写回的草稿。这时只有内存残片，工具会明确说"关掉→重开→尽快送"，不会含糊报"对不上" |
| 只处理"当前打开的那一份" | 一次一份，不支持批量/后台扫所有草稿 |
| 高版本密文 | 剪映 11.7 起密钥收进 `crypto_key_store.dat`，磁盘上没有可用的解密路径，所以只能走明文这条路 |

### C. 送不进达芬奇的东西（每次送入都会打印，写回全部保留）

| 元素 | 为什么 | 写回保留 |
|---|---|---|
| 蒙版 / 蒙版关键帧 | 脚本接口无蒙版入口，`AddClipMatte` 也试过 | 是 |
| 文本 / 字幕 | 字幕轨要 Subtitle 对象，接口写不了文字 | 是 |
| 贴纸 | 剪映私有素材包 | 是 |
| 滤镜轨、视频特效 | 剪映私有效果包，不是标准 LUT | 是 |
| 入场/出场动画、段关键帧 | 关键帧曲线无法经 `AppendToTimeline` 写入 | 是 |
| 画面缩放/位移/旋转/裁切 | 接口不收变换参数，达芬奇按原素材铺满 | 是 |
| 变速 | 无速度接口，只能 bake 或占位对齐 | 是（真变速靠 bake） |
| 曲线变速 | bake 只能按平均速度做恒定变速，**曲线节奏被拉平** | 是 |
| 转场 | 接口不能建转场，只能"后段起点收前段时长"近似 | 是 |
| 独立音频轨、音量/淡入淡出 | 音频不送（调色不需要声音） | 是 |
| 调节（HSL / 曲线） | 属于调色，应在达芬奇里重做 | 是 |
| 图片素材 | 链路只走视频素材，图片段整段跳过 | 是 |
| 复合片段内部的装饰 | 达芬奇里的复合片段是用内部视频素材重新合成的 | 是 |

### D. 观感层面的近似（结构对、观感会有差）

| 限制 | 影响 |
|---|---|
| 转场是"收短近似" | 达芬奇里没有真实转场，会有硬切；位置和总长对得上 |
| 曲线变速被拉平 | 帧位/总长对得上，节奏感不一样 |
| 画面变换不带 | 达芬奇里按原素材铺满，构图会变（报告会点名是哪几段） |
| 复合片段内部装饰丢失 | 只有内部视频素材参与重新合成 |
| 断言保结构，不保观感 | 它保证"剪映原生结构一段不差"，不保证"看起来一模一样" |

### E. 行为约束

| 限制 | 说明 |
|---|---|
| 写回只认"送入那一刻的快照" | `runs\<草稿ID>\snap-<时间戳>\`。之后在剪映里怎么剪都不影响这次往返，也不会覆盖你后来的改动 |
| 写回生成**新草稿**，不覆盖原稿 | `xxx_调色`、`xxx_调色_2`… 版本会增殖，工具不替你删（那是你的成片版本） |
| `runs` 目录永不自动回收 | `snap-*/` 是写回唯一底稿，删了就再也写不回去 |
| 变速 bake 要花时间与磁盘 | 每段编码一次，落在 `retime\<草稿ID>\`，30–60 MB；没有 ffmpeg 会退回占位对齐并说明 |
| 只能"整条时间线"往返 | 不支持只送选中的几段（片段级往返是另一家的做法） |

## 6. 视频脚本

### 6.1 三分钟版

### 6.2 三十秒版（信息流 / 短视频）

1. （5 秒）剪映时间线：「剪映剪完，想去达芬奇调色，又不想重剪？」
2. （8 秒）点 ①，达芬奇时间线出现：「点一下，整条时间线进达芬奇，按帧对齐。」
3. （7 秒）调色：「正常调，Resolve 原生。」
4. （5 秒）点 ②，剪映新草稿：「调完点一下，LUT 回到剪映。」
5. （5 秒）继续拖片段：「而且还能接着剪。」

## 7. 不要说的话（避免翻车）

| 别说 | 为什么 | 改成 |
|---|---|---|
| 「无损往返」「完美同步」 | 转场是近似、曲线变速被拉平、画面变换不带 | 「结构一处不差，观感有三处近似」 |
| 「所有效果都能带过去」 | 13 项不送清单是硬的 | 「带不过去的会逐项打印，写回时全部保留」 |
| 「替代达芬奇的剪辑」 | 定位就是"剪映剪、达芬奇调" | 「只做调色这一段往返」 |
| 「不用打开剪映」 | 明文依赖剪映进程 | 「剪映开着、草稿打开，这是前提」 |
| 「一键、零配置、人人可用」 | 要装 ffmpeg（变速）、要认路径 | 「装一次，之后就是三个按钮」 |
| 「比某某工具快 N 倍」 | 没有同条件的公开基准 | 「省掉导 XML 和重剪这两步」 |
| 「某某工具是垃圾 / 骗钱」 | 指名贬损有法律风险，也没必要 | 只讲技术路线差异：「它搬工程，我搬时间线」 |

> 指名对比时，尽量引对方**原文措辞**（"渲染成片""保存为预设""不支持转场"），而不是替它下结论。这样既有说服力，也不会被反驳。

## 8. 演示前的检查单（拍摄用）

- [ ] 剪映里准备一份"什么都有"的草稿：多轨、变速、主轨转场、蒙版、一段**停用**的片段
- [ ] 达芬奇里清空/新建一个工程，别留别人的时间线（会被闸门拒绝）
- [ ] 面板缓存行确认显示「可清理：无」或少许，避免拍到脏状态
- [ ] 草稿**刚重开过**（拍之前不要编辑），否则会弹"请重开草稿"
- [ ] 录屏分辨率至少 1080p，达芬奇时间线缩放到能看清轨层
- [ ] 先跑一遍完整流程热身（缓存会建立，正式拍时是秒级）
