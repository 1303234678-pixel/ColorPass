# 剪映草稿字段速查

这份表来自本仓库在一台 Windows 机器上的实测（剪映专业版 **11.7.0**），不是从
别处抄的文档。**标 ⚠️ 的是没验证过的推断**，不要当结论用。

## 1. 一份草稿里有什么

```
<草稿目录>/<工程名>/
├── draft_content.json          主时间线（11.7+ 是 base64(AES) 密文）
├── draft_meta_info.json        元信息（明文）
├── draft_settings              明文 INI：草稿设置 + draft_last_edit_time
├── draft.extra                 运行期数据（打开一段时间后写入）
├── .locked                     存在且新鲜 = 剪映认为它开着；mtime 约等于打开时刻
├── .backup/<时间戳>_<hash>.load.bak   载入前的备份（来源决定明文还是密文）
├── Timelines/<uuid>/draft_content.json   多时间线时的分文件
└── Resources/                  素材、缓存
```

时间单位全是**微秒**（`target_timerange.duration` = 4,000,000 表示 4 秒）。

## 2. 时间戳怎么判断

| 字段 | 可信度 | 说明 |
|---|---|---|
| `draft_settings` 的 `draft_last_edit_time` | ✅ 高 | 明文，用户最后一次编辑的时间 |
| `.locked` 的 mtime | ✅ 高 | 约等于「打开这份草稿」的时刻 |
| `draft_content.json` 的 mtime | ❌ **不可用** | 打开草稿时剪映会自己写一次盘（实测与打开时间只差 1 秒），不代表内容变了 |
| `.backup/*.load.bak` 的文件名时间戳 | ✅ 可用 | 备份发生时刻 |

判断「打开之后有没有改过」：`draft_last_edit_time > .locked mtime`。几十毫秒出结果，
不用扫内存。

## 3. 段（segment）

```jsonc
{
  "id": "…",
  "material_id": "…",                    // 指向 materials.videos/photos
  "target_timerange": {"start": 0, "duration": 4000000},   // 时间线上的位置
  "source_timerange": {"start": 0, "duration": 4000000},   // 素材内的入点与长度
  "extra_material_refs": ["…"],          // 变速 / 蒙版 / 转场 / 动画 / 滤镜 …
  "speed": 1.0,                          // 有的版本写在这里
  "visible": false                       // 停用片段；正常段**没有这个键**
}
```

**停用片段**是 `visible: false`，不是 `disabled`。全库搜不到 `disabled` 键。
`enable_hsl=false` / `enable_adjust_mask=false` 只是「这个功能没开」，与停用无关。
停用段**仍然占着时间线**，跳过不送会让后续每段位置全错。

## 4. 材质（materials）

| 键 | 内容 | 备注 |
|---|---|---|
| `videos` / `photos` | 素材：`path`、`width`、`height`、`duration` | 路径写错时剪映仍可能按 `resource_id` 找到 |
| `speeds` | 变速：`speed`、`curve_speed.speed_points` | 曲线变速时 `speed` 只是平均值，节奏在 `speed_points` |
| `transitions` | 转场：`name`、`duration` | 挂在**前一段**的 `extra_material_refs` 里 |
| `masks` | 蒙版：`name`、`config` | 只用于报告与写回核对，本工具不送蒙版 |
| `effects` | 特效 / LUT：`path`、`resource_id` | 写回时新增的 LUT 也是这个形状 |
| `drafts` | 复合片段：`draft_file_path` → `subdraft/<uuid>/draft_content.json` | 内部是一份完整的子草稿 |
| `texts` / `stickers` / `audios` / `filters` | 文字 / 贴纸 / 音频 / 滤镜 | 本工具不送入达芬奇 |

## 5. 明文从哪来

| 来源 | 何时可用 | 校验 |
|---|---|---|
| 进程内存 | 剪映打开着草稿，且明文**尚未被回收** | 按体积对账（容差 320 B + 0.5%）+ id 匹配 |
| `.backup/*.load.bak` | 备份是明文时（我们写回的草稿就是明文） | id 匹配 + 编辑时间不晚于备份时间 |
| 本地缓存 `%LOCALAPPDATA%\JYBridge\plain\` | 之前成功读过，且磁盘指纹（载荷字节数 + 编辑时间）没变 | 指纹完全一致 |

**明文会被回收**：实测一份打开一小时、从未编辑的草稿，内存里只剩 167 KB 残片
（有 `"tracks":[`、没 `"materials"`、括号不闭合）。这与是否编辑无关。

**载入备份不能用体积卡**：加载器序列化比落盘版长 14%（73,683 vs 63,143 B），
只能靠编辑时间判新旧。

## 6. 写回时剪映接受什么

- 写**明文** `draft_content.json`，剪映打开后会自己重写成密文（11.7.0 实测）。
- 复合片段会按 `draft_file_path` 去加载原件，所以写回用的是**克隆 + 只追加 LUT
  材质**，不重建结构。
- 新增 LUT 材质放在新草稿自己的 `Resources/JYBridge/`，跟着草稿走，换机器也在。

## 7. 版本矩阵

| 剪映 | 状态 | 说明 |
|---|---|---|
| 11.7.0 | ✅ 实测 | 本文所有数字来自这个版本 |
| 11.8 / 12.x | ⚠️ 未验证 | 字段大概率兼容，明文路线需实测 |
| 11.2 / 11.3 | ⚠️ 未验证 | 有第三方项目用 `videoeditor.dll` 在这两个版本上解密 |
| ≤ 10.6 | ⚠️ 未验证 | 结构差异较大，本工具未适配 |

升级剪映后如果 `check` 报 `no_plaintext`，先按提示关掉草稿重开一次；仍然失败请
用「版本不兼容」模板提 issue。
