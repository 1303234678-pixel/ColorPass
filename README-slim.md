# JYBridge · 剪映 ⇄ 达芬奇往返

剪辑以剪映为准，达芬奇只调色。面板里只有三个按钮：**① 送入达芬奇**、**② 写回剪映（按送入那版）**、**锁定/解锁轨道**，外加一个「新草稿名」输入框（留空＝`<草稿名>_调色`，同名自动 `_2`）。

面板顶部一行是**当前草稿**和 **↻ 刷新**：打开面板时自动扫一次，剪映里换草稿后点刷新。
**没扫到草稿时 ① 和 ② 是灰的**，点不动 —— 这两个动作的前提就是剪映里有一份打开的草稿，
让它点下去再吃闸门报错是白跑一趟。任务执行期间所有按钮也会临时禁用。

下面还有一行**可清理的缓存量 + 清理缓存**，见「缓存会不会越积越多」。

**结果只留一行**：成功时显示「送入完成：13 段（精确对齐 13 段）· 时间线 JY · 11月18日」，
下面最多两行附注（`不送：蒙版 2、文本 1` / `画面变换：1 段…`）—— 报告正文不再显示在面板上。
**失败时弹独立小窗**，写清原因和处理步骤，带「重试」按钮；弹窗不阻塞面板，关掉即可继续。
完整报告仍在 `%LOCALAPPDATA%\JYBridge\runs\<草稿ID>\` 下的 json 里。

## 改过草稿要重新打开 —— 这是剪映的内存行为

在剪映里打开一份草稿、做了改动并保存之后，**点「① 送入达芬奇」会当场弹提示**，
要你先重开草稿。不是 bug，是这一版剪映的实测机制：

- 打开草稿时，剪映把 `draft_content.json` 解密进内存；这份明文**只保留一段时间**，
  打开久了会被它自己回收（见下一节）；
- 之后的每次编辑/保存，磁盘上的密文会更新，但内存里那份**还是打开那一刻的版本**；
- 保存动作还会把编辑时临时生成的明文副本回收掉，所以内存里找不到新版。

判据两条，**都不扫内存**（几十毫秒出结果，所以点下去就弹，不用等半分钟）：

1. `draft_settings` 里的 `draft_last_edit_time` 晚于 `.locked` 的建立时刻 ——
   草稿在打开之后又被编辑过。这条能抓住「只改了一个字、体积几乎没变」的小改动；
   反过来，剪映打开草稿时自己写一次盘（实测相差 1 秒）不会误报，因为那次写盘
   不前进 `last_edit`。
2. 内存明文体积 vs 磁盘密文载荷（容差 320 B + 0.5%）—— 送入口的第二道，
   抓「整体版本不一致」：多份内存副本、换过版本、体积差得远。

面板上还会顺手标出来：草稿名后面一个 `· 已改`，状态行写清「打开之后又被编辑过
（最后编辑 23:47:41）」。

**处理只有一条**：把草稿关掉（回到剪映首页），再双击重新打开，然后点弹窗上的
「我已重开，再试」。`Ctrl+S` 没用，切到别的草稿再切回来也**不管用**（那不是重新解码）。

反过来也成立：**打开草稿后直接送入 ① 是安全的**；② 写回读的是送入那一刻的快照，跟剪映内存无关，
所以调完色直接写回不受这条限制。要是想省事，就按「先送入 → 到达芬奇调 → 再写回」的顺序做，
中间别在剪映里改剪辑。

## 明文读不到时，还有两条不靠内存的路

剪映**不会一直**把明文留在进程内存里。2026-11-20 实测：一份 23:38 打开、
全程没动过的草稿，到 00:38 再扫，内存里只剩 167 KB 的残片（有 `"tracks":[`，
却没有 `"materials"`，括号都不闭合）—— 用户什么都没改，只是挂在那儿一小时。
这时点送入，旧版本会报「内存明文与磁盘密文对不上」，等于把责任推给用户。

现在按顺序试三个来源，前两个都是**秒级**的文件操作：

| 顺序 | 来源 | 什么时候成立 | 校验 |
|---|---|---|---|
| 1 | 本地缓存 `%LOCALAPPDATA%\JYBridge\plain\<草稿ID>.json` | 以前成功读过这份草稿 | 磁盘指纹（密文载荷字节数 + 最后编辑时间）**完全一致** |
| 2 | 剪映载入备份 `<草稿>\.backup\*.load.bak` | **我们写回的草稿**：明文写进去，备份也是明文 | id 等于当前主时间线；最后编辑时间不晚于备份时间 |
| 3 | 扫进程内存 | 上面两条都不成立 | 内存明文体积 vs 密文载荷（容差 320 B + 0.5%） |

第 1 条是唯一能长期生效的：每次成功读出明文都会存一份带指纹的副本，磁盘没再
存过盘就一直有效。第 2 条只在「写回后第一次打开」是明文 —— 剪映自己保存成密文
之后，备份也跟着变回密文；但它正好补上「刚写回、还没送过」这段空白。

第 2 条**不能**用体积去卡：剪映的载入备份是加载器序列化，同一份内容比落盘版长
14%（实测 73683 B vs 63143 B），拿内存那套容差会误拦。它靠「最后编辑时间」判新旧。

三个来源都拿不到时，报的是专门的 `no_plaintext`（不是含糊的「对不上」），
弹窗直接给三步：关掉草稿 → 双击重开 → 重开后尽快点一次送入。重开时剪映会重新
留一份明文，成功送一次之后缓存也就有了。

## 三条硬规矩（都是实测踩出来的）

1. **送入要求**：剪映在跑且目标草稿确实打开（目录里有新鲜 `.locked`）、达芬奇在跑且**没有别人的时间线**。达芬奇停在项目管理器时会自动新建一个空白工程；工程里只有本工具建的 `JY · …` 时不算阻塞（建时间线会自动换名）。不满足直接停，一个字不写。
2. **写回只认「送入那一刻的快照」**：`%LOCALAPPDATA%\JYBridge\runs\<草稿ID>\snap-<时间戳>\`。之后你在剪映里怎么剪都不影响这次往返，新草稿也不会覆盖你后来的改动。
3. **变速只能预渲染**：达芬奇脚本接口没有设置片段速度的入口（26 个属性键里没有 Speed，11 个候选方法全是 None）。`bake` 用 ffmpeg 把源区间重采样成等长 ProRes，帧序与剪映一致；机器上没有 ffmpeg 会自动退回 `slot`（占位对齐）并在报告里写明。

## 蒙版策略：完全不进达芬奇

蒙版是固定不送的，不是「送失败」：

- **原因**：`TimelineItem` 的 26 个属性键与全部候选方法里没有任何蒙版入口，`AddClipMatte` 也不行（实测逐个试过）。
- **做法**：送入时只给段打 `has_mask` 标记，不改任何摆放参数，不报错、不阻断。日志与 `send.json` 的 `masks` 字段列出段 ID、轨道、时间点、蒙版名、蒙版关键帧数。
- **写回**：新草稿从送入快照克隆，蒙版（含关键帧）原样带回，`write.json` 的 `masks_unchanged` 逐段核对。
- **体检**：`audit` 的 `facts.masks_not_sent` 列出明细，不产生 blocking。

## 停用片段：照送，但让达芬奇也别渲染

剪映里「停用」的片段是段上的 `visible: false`（正常段根本没有这个键，实测全库只有这一处）。这类段**不能跳过**：

- **它仍然占着时间线**。取消停用时时间轴不会动，跳过的后果是达芬奇里留一块黑场，并且后面每一段的位置核对全部错位。
- **做法**：照常 `AppendToTimeline` 落轨，落完调 `TimelineItem.SetClipEnabled(False)`。达芬奇的「禁用片段」是同一件事：占位、不出画面、随时可再启用。
- **不预渲染**：停用段即使带变速也不进 bake —— 看不见，没必要为它转一次码。
- **取色跳过**：`pull` 遇到禁用片段不导 LUT。给停用段塞一个恒等 cube，用户一取消停用就会多出一层处理；写回也不因此判失败（`want=None, got=None` 视为正确）。
- **写回断言**：`visible` 进了结构指纹。克隆如果把停用段变回启用，会被判失败 —— 否则被关掉的画面会「复活」进成片，而其它断言全过。
- **老版本**：没有 `SetClipEnabled` 的 Resolve 上不判整次送入失败，但 `send.json` 里 `disabled_unsupported: true`，并说明这段在达芬奇里仍会出画面。

`cli check` 的 `features.segments_disabled` 是同一口径的计数。

## 送不进达芬奇的东西（每次送入都会打印）

`send.json` 的 `not_sent` 逐项给出 `feature / count / why`，`writeback=true` 表示写回时按快照原样保留：

| 元素 | 为什么送不进去 | 写回保留 |
|---|---|---|
| 蒙版 / 蒙版关键帧 | 脚本接口无蒙版入口 | 是 |
| 文本 / 字幕 | 字幕轨要 Subtitle 对象，接口写不了文字 | 是 |
| 贴纸 | 剪映私有素材包 | 是 |
| 滤镜轨、视频特效 | 剪映私有效果包，不是标准 LUT | 是 |
| 入场/出场动画、段关键帧 | 关键帧曲线无法经 AppendToTimeline 写入 | 是 |
| 画面缩放/位移/旋转/裁切 | AppendToTimeline 不收变换参数，达芬奇按原素材铺满 | 是 |
| 变速 | 无速度接口，只能 bake / 占位对齐 | 是（真变速靠 bake） |
| 曲线变速 | bake 只能按平均速度做恒定变速，曲线节奏会被拉平 | 是 |
| 转场 | 接口不能建转场，用「后段起点收前段时长」近似 | 是 |
| 独立音频轨、音量/淡入淡出 | 音频不送（调色不需要声音） | 是 |
| 调节（HSL / 曲线） | 属于调色，应在达芬奇里重做 | 是 |
| 图片素材 | 这条链路只走视频素材，图片段会被整段跳过 | 是 |
| 复合片段内部的装饰 | 达芬奇里的复合片段是用内部视频素材重新合成的 | 是 |

> 只有「变速」会影响达芬奇里的观感但已用 bake 解决；「画面变换」和「曲线变速」是剩下两处会看出差别的地方，报告里会单独点出具体是哪几段。

## 缓存会不会越积越多（2026-11-19 加的机制）

**会，所以做了自动回收。** 每送一次草稿，`%LOCALAPPDATA%\JYBridge\` 下就会按草稿 ID 留一份痕迹，剪映里把旧草稿删了也不会有人来收：

| 目录 | 内容 | 单份大小 | 参与回收 |
|---|---|---|---|
| `luts\<草稿ID>\` | 取回时导出的 cube 工作副本 | 约 12 MB | 是 |
| `retime\<草稿ID>\` | 变速段 ffmpeg 预渲染的 ProRes | 30~60 MB | 是 |
| `runs\<草稿ID>\` | 报告 + `snap-*/` 底稿快照 | 0.2~几 MB | **否** |

luts 与 retime 是**可再生的中间产物**：cube 在写回时已经复制进新草稿自己的
`Resources\JYBridge\`，retime 素材随时能重编 —— 删掉不会让已经写回的草稿丢 LUT
（它用的是草稿目录里那一份）。

`runs` 例外，它**不进回收池**：`snap-*/` 是写回唯一的底稿（连复合片段的子草稿副本一起），
删了那份草稿就再也写不回去 —— 而 `runs` 的旧版本每次送入都会自动清理，一个草稿只占
几百 KB，本来也不值得回收。

**四道闸**（`jybridge/gc.py`）：

1. **活动草稿永不动** —— `current.json` / `pending.json` 指着的 draft_id 全程保护，写回还要用它的快照。
2. **孤儿草稿直接收** —— `runs\<id>` 里记的源草稿名在剪映草稿目录里已经不存在了，
   那份 luts/retime 再也用不上（这份报告本身留着，它是判据，不占多少地方）。
3. **太旧 / 太多** —— 超过 30 天没动，或每个池只留最近 5 份。
4. **总量兜底** —— 前面过完还超过 600 MB，从最老的继续收。

什么时候跑：

- **自动**：`send` / `write` / `roundtrip` 成功后各跑一次，用更宽松的阈值（最近 8 份 / 60 天 / 1.2 GB），只在明显堆积时才动手；失败不影响这次往返的结果。
- **手动**：面板上的「清理缓存」，或命令行 `gc`（默认只列清单，加 `--apply` 才删）。

```bat
python -m jybridge.cli gc                                   :: 只报告：哪些能收、收多少
python -m jybridge.cli gc --apply                           :: 真删
python -m jybridge.cli gc --apply --keep-last 3 --max-mb 400
python -m jybridge.cli gc --intermediate                    :: 只清「可再生中间产物」
```

**面板那行报的是「真能删掉的量」，不是缓存目录的总占用。** 总占用里大头是写回要用的
底稿快照和当前草稿的 cube，按设计就删不得 —— 把 85.9 MB 报成「缓存」，点完却 0 项、
数字纹丝不动，只会让人认定按钮坏了。所以删不掉的部分干脆不显示，三种状态：

| 面板显示 | 含义 | 按钮 |
|---|---|---|
| `可清理：12.3 MB` | 默认四道闸会收掉的 | 可点，按默认策略删 |
| `可清理：可再生 42.1 MB` | 只剩余可再生的中间产物 | 可点，一次跑 `gc --apply --intermediate` |
| `可清理：无` | 一项都收不掉 | **灰的**，不给你点了没反应的按钮 |

第二种最常见：三份以内的活跃草稿都在保留期内，默认策略一分不动，能腾的只有
中间产物。点下去直接清，不再多弹一层窗问一遍。`--intermediate` 的范围：

- 收：`retime\<草稿ID>\`（变速预渲染的 .mov）和 `luts\<草稿ID>\`（cube 工作副本）；
- **不收**：`runs\<草稿ID>\`（报告 + 写回要用的底稿快照）。快照在，那份草稿就还能写回；
- 活动草稿（`current.json` 指着的）一律跳过；
- 代价：这些文件下次送入同份草稿时会自动重新生成，**变速段要多渲染一次**。

以 2026-11-19 的实测为例：目录总共 85.9 MB，默认策略可回收 0，面板显示
`可清理：可再生 44.1 MB`（另一份草稿的 retime + cube）；清掉之后剩 41.8 MB
（当前草稿的快照与 cube），当前草稿一个字没动。

**剪映那侧的 cube 不归它管**：每次写回都会生成一份**新草稿** `xxx_调色`，cube 嵌在那份草稿的
`Resources\JYBridge\` 里，跟着草稿走 —— 草稿在，LUT 就在；你在剪映里删掉旧草稿，它带的 cube
一起消失。反复写回会留下 `xxx_调色`、`xxx_调色_2`…，这些属于你的成片版本，工具不会替你删。

## 命令行（面板调的就是这些子命令，同一条链路）

```bat
python -m jybridge.cli status     :: 秒级：剪映在不在、哪份草稿、上次送入、缓存占用
python -m jybridge.cli gate       :: 只查前置条件，不动任何东西
python -m jybridge.cli newproj    :: 让达芬奇新建一个空白工程并进入
python -m jybridge.cli send [--speed=bake|slot|source]
python -m jybridge.cli write [--name 新草稿名]
python -m jybridge.cli roundtrip  :: 送入→取回→写回，一条命令跑完
python -m jybridge.cli audit      :: 全项体检（结构/素材/时长/风险/不送清单）
python -m jybridge.cli reset      :: 丢掉「没走完的那次送入」
python -m jybridge.cli clean      :: 清变速预渲染缓存（整池清）
python -m jybridge.cli gc         :: 按策略回收缓存（默认只报告）
```

报告都落在 `%LOCALAPPDATA%\JYBridge\runs\<草稿ID>\`：`send.json` / `plan.json` / `pull.json` / `manifest.json` / `write.json`。

**重复送入**：同名时间线有内容时自动用 `JY · 草稿 (2)`、`(3)`，绝不覆盖已调色的那条；空的同名时间线会删掉复用。工程里已有本工具的时间线时不再改工程帧率/分辨率（免得已调色的时间线重算）。
