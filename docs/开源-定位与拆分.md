# 开源定位与拆分方案

> 数据口径：2026-11-20，GitHub REST API 实取。
> 目的：决定「开源什么、怎么切、怎么讲」，让这个项目在 GitHub 上被看懂、被引用、被 star。

---

## 0. 一句话结论

**星数最高的方案解决的是「让程序生成草稿」，你解决的是「让两个软件互换工程」。**

这两件事的受众、复用方式、star 逻辑完全不同。所以：

- 不要拿 4,942 星的 `pyJianYingDraft` 当对标——它服务的是 Python 自动化开发者，你服务的是剪辑师。
- 你的 star 上限不在「完成度」，在「**能不能被单独拿走用**」。现在所有能力都焊在达芬奇面板里，别人拿不走，所以再强也只有个位数星。
- 开源的正确动作不是「把仓库公开」，而是**让能力能脱离达芬奇被单独使用**：一个可 `pip install` 的包、三条清晰的层边界、两个离线就能跑的 CLI（`check` / `plan`），面板只作为参考实现。

## 2. 三个核心创新点（按「能不能被单独拿走」排序）

不要列七个卖点。开源仓库的首屏只能容纳三个概念，多了就没人记得住。

### 创新点 A · 读得到：加密草稿的明文三级回退

**问题**：剪映 11.7+ 的 `draft_content.json` 是 base64(AES) 密文，密钥由进程启动时注入、不在磁盘上。公开方案到这里全部止步，标准答案是「请重开剪映」。

**你的解法**（`jybridge/plain.py` 245 行 + `draftio.freshness()`）：

| 层 | 来源 | 生效条件 |
|---|---|---|
| 1 | 本地缓存 `%LOCALAPPDATA%\JYBridge\plain\<id>.json` | 磁盘指纹（密文载荷字节数 + `draft_last_edit_time`）完全一致 |
| 2 | 剪映载入备份 `<草稿>/.backup/*.load.bak` | 我们写回的草稿是明文写入 → 备份也是明文；id 匹配且编辑时间不早于备份 |
| 3 | 进程内存扫描（体积对账，容差 320 B + 0.5%） | 明文还没被回收 |

**为什么这是创新点而不是补丁**：

- 实测结论：明文**只保留一段时间**。一份 23:38 打开、从未编辑的草稿，到 00:38 内存里只剩 167 KB 残片（有 `"tracks":[`、没 `"materials"`、括号不闭合）。**与用户是否编辑无关。** 公开资料里没人记录过这条。
- 载入备份**不能用体积卡**：加载器序列化比落盘版长 14%（73,683 vs 63,143 B），只能靠编辑时间判新旧。这种反直觉细节是这个模块的真正含量。
- 效果：`cli check` 从 25 秒失败 → **0.78 秒成功**。

**它作为独立包的价值**：任何要读剪映草稿的项目（4,942 星的 pyJianYingDraft 至今仍在 README 里写「模板模式需 `fallback_loader`」）都需要这一层。这是**最可能被别人 import 的一块**。

---

### 创新点 B · 摆得准：草稿语义 → NLE 时间线的无损落轨

**问题**：XML / AAF 里没有「这一段是 2 倍速」「这一段被停用」这些属性。导进去按原速摆，5 秒段变 10 秒，**后面每一段全错位**。这就是所有同类工具用户反馈「导进去位置不对」的根因。

**你的解法**（`jybridge/send.py` 984 行）：

| 草稿里的东西 | 常见工具 | 你 |
|---|---|---|
| 变速 | 丢掉（或只提示「可能对不上」） | ffmpeg 预渲染等长 ProRes，帧序与剪映一致 |
| 转场 | 丢掉 | 「后段起点收前段时长」消解重叠，位置不偏 |
| 停用段 `visible:false` | 当正常段送 → 画面「复活」 | 照样占位，落轨后 `SetClipEnabled(False)` |
| 复合片段 | 丢掉 / 拍平 | 递归展开，`depth` 限深 |
| 帧率不一致 | 累积误差 | 绝对帧号 `AppendToTimeline` |

**停用段这一段值得单独讲**：它仍在时间线上占位（实测主轨只到 6.533 s，整条 12.267 s 有 5.5 s 靠这条停用段撑着）。所以「跳过不送」会让达芬奇里出现黑场并让后续核对全错。正确处理只有一种：落轨 + 禁用。

**它作为独立包的价值**：`build_plan(draft) -> [计划条目]` 是一个**纯函数**，输入草稿 JSON、输出可 dry-run 的落轨计划。不需要达芬奇就能跑，也不需要写 XML。这个接口形态本身就容易被别人接。

### 创新点 C · 回得去：调色意图的回传协议（最硬的一块）

**问题**：全行业没人解决「调完色怎么回剪映还能继续剪」。现有做法只有两种，都很脏：

- 渲染成片 → 塞进草稿副本 → 回剪映是一块不可编辑的肉（LMbox 彩虹桥、片段级桥接插件）
- 重建草稿 → 只能保留剪辑点，特效/滤镜/蒙版从一开始就不存在（CutConvert、Free Forever）

**你的解法**（`pull.py` + `write.py`）：

```
达芬奇调色
  → 每段打一个 marker，custom data 写 segment_id（身份锚）
  → 逐段 ExportLUT(EXPORT_LUT_33PTCUBE) → 33³ = 35,937 个采样点
  → 拿送回时存的底稿快照做深拷贝（不是重建）
  → 只 append 一条 LUT 效果材质，时间线一个字节不动
  → 三道断言全部通过才落盘，否则拒绝写回
```

**三个断言是这套东西的护城河**（`write.py:structure_index / structure_diff`）：

- 比的是**语义指纹**：轨道类型、段顺序、入出点、素材引用、变速倍率、关键帧、转场/蒙版/变速/淡入淡出/复合片段引用
- **只比语义不比 id** —— 所以新加的 LUT 材质不会误报
- **失败即拒绝**：`rep["ok"]` 要求全过，宁可告诉你写回失败，也不给你一份「看着对、其实丢了东西」的草稿
- 有一条专门的故障注入测试：把克隆后的 `visible:false` 删掉 → 必须判失败

**为什么这是最强的一条**：别人在「搬工程」，你在「搬可编辑结构 + 调色意图」。竞品一个断言都没有，全靠肉眼。这条讲出来是降维的。

## 4. 拆包方案

> **执行记录（2026-11-20）**：按本节落地时改成了**单包 + 三层**，理由见 4.1 末尾。
> 三个 PyPI 名字是「发布决策」，不是「代码结构」；边界已经在代码里收紧了。

### 4.1 实际形态：一个可安装包，三层边界

```
jybridge/                    pip install -e .  →  jybridge <子命令>
├── L0 环境与明文来源
│   ├── paths.py             目录约定（LUT / 报告 / 明文缓存）
│   ├── probe.py             认剪映工程（进程、窗口、草稿目录、锁）
│   ├── memscan.py           进程内存扫描（Windows ReadProcessMemory）
│   └── plain.py             缓存 + 载入备份 + 内存，三级仲裁
├── L1 草稿语义
│   └── draftio.py           轨道/变速/转场/蒙版/复合片段 + 新鲜度判定
├── L2 动作
│   ├── send.py              草稿 → 达芬奇：plan / 落轨 / 变速 / 停用段 / marker
│   ├── pull.py              达芬奇 → 33³ LUT（marker 作身份锚）
│   ├── draftbuild.py        克隆底稿 + 追加 LUT 材质
│   ├── workflow.py          write_back 编排（面板与旧脚本共用）
│   └── write.py             写回 + structure_diff 语义断言
├── L3 壳
│   ├── cli.py               命令行（check / plan / send / pull / write / gc）
│   └── panel/               达芬奇面板（参考实现）
└── templates/               扁平草稿模板
```

**为什么没拆成三个包**：三块之间共享 `draftio` 的语义索引（`layers` / `speeds_by_ref` /
`expand_compound`），真拆需要把语义层再提一层公共依赖，改动面比收益大；而「能被单独
安装」这个目标，靠**依赖方向**已经达成 —— L0 可以只 import 标准库，`draftio` 不再碰
`send` / `write` / `workflow`。真要发三个包，是给同一份代码加三个 `pyproject` 的事。

**已经做掉的那一步重构**：

> `draftio.py` 顶层曾有 `import jy_workflow as WF` —— **读取层反向依赖编排层**，
> 导致「读草稿」必须把达芬奇那套编排一起拖进来。现在改为 `from . import probe, memscan`，
> 内存扫描逻辑内联成 `draftio._scan_open_draft()`（前后各拍一次身份快照）。
> `app/` 整个目录已并入 `jybridge/`，仓库里只剩一个包。

### 4.2 每个能力都要有「不需要达芬奇就能跑」的一屏

这是能不能被 star 的分水岭。别人 clone 下来，不能什么都做不了。

| 能力 | 一屏命令 | 输出 |
|---|---|---|
| 读草稿 | `jybridge check` | 草稿结构报告 JSON（轨道/段数/停用段/明文来源/新鲜度） |
| 落轨计划 | `jybridge plan` | 落轨计划 JSON（lane / 起始帧 / 时长 / bake 标记 / 重叠消解）—— **dry-run，不碰达芬奇** |
| 写回核对 | `write.structure_diff(a, b)` | 结构差异（「变速倍率变了」「停用状态被改回」） |

三个都是**离线可跑、可进 CI、可被别人当工具用**的。这比「一个需要装达芬奇才能看的面板」传播力高两个量级。

## 7. 开源前必须先处理的三件事

### 7.1 许可证（现在没有 LICENSE 文件）

没有 LICENSE = 默认保留所有权利，别人**不能合法使用**，开源等于白开。

| 选择 | 适合 | 代价 |
|---|---|---|
| **MIT** | 传播最快，个人/商用都无门槛 | 无专利条款 |
| **Apache-2.0** | 与 pyJianYingDraft 一致，含专利授权 | 稍啰嗦，需 NOTICE |

建议 **Apache-2.0**：这套东西含「方法」（LUT 回传协议、语义断言），专利授权条款对后来者更友好，也更像基础设施。

### 7.2 EULA 灰区，必须在 README 里主动写清

你做的事包含：**扫剪映进程内存**、**写明文草稿让剪映重新加密**。这在灰区，必须自我约束并声明：

- 只读本机、当前用户自己的草稿；不上传、不联网
- 不绕过 VIP / 不破解授权 / 不解密他人文件
- 明文只在本机缓存，滚动保留 12 个
- 提供一个 `--no-memscan` 开关（纯缓存 + 备份模式），给介意的人

主动写清楚，比等人来问强。这也是 issue 质量的分水岭。

### 7.3 维护成本要提前认

| 风险 | 表现 | 缓解 |
|---|---|---|
| 剪映升级改动明文/字段 | 三级回退全失效 | README 顶部放版本矩阵 + 「最后一次实测版本」 |
| 达芬奇 API 差异 | `SetClipEnabled` 在 17 没有 | 已有 `disabled_unsupported` 降级，写进文档 |
| issue 大多是「我的版本不行」 | 维护疲劳 | issue 模板强制填三件事：剪映版本 / 达芬奇版本 / `cli check` 输出 JSON |

## 8. 如果只能推一件事

**把「读得到」这一层推到台前：`plain` + `memscan` + `probe`。**

理由：

- 它解决的是所有剪映工具的共同痛点，受众最大（4,942 星那个项目的 README 至今还在教用户传 `fallback_loader`）
- 245 + 453 + 15,762 字节，纯 stdlib + ctypes，无达芬奇依赖，可离线测试
- 它**唯一能被「不需要达芬奇的人」用上**：`jybridge check` 一条命令就出结构报告
- 一旦有人拿它读草稿，`send` / `pull` / `write` 和面板就有了自然流量

现实中的形态是：一个 `pip install jybridge`，但 README 首屏、视频、话题标签先讲「读得到」，
另外两层随后跟上，面板最后作为「参考实现」出现在文末。
