# 送入耗时：测出来的瓶颈和改法

> 用户反馈「送入花了 1 分多钟」。结论：**80 秒花在变速段预渲染上**，而且编出来
> 的中转文件是 4.5 GB。原因是按**源分辨率**（4K）编 ProRes，而时间线是 1080p。
> 缩到画布后同一条时间线 34 秒 / 1.4 GB，画面逐帧一致。

## 1. 怎么定位的（不靠猜）

`send.json` 每次都会落在 `%LOCALAPPDATA%\ColorPass\runs\<草稿ID>\`。这一次的三条线索：

| 线索 | 值 |
| --- | --- |
| 快照目录建立时间 | 02:16:35 |
| 预渲染产物落盘时间 | 02:18:0x |
| `baked[0].want` | 1903 帧（63 秒，1.4535 倍速） |
| 产物大小 | 4,523,563,281 B（4.5 GB） |
| 源素材 | `DJI_0188.MP4`，3840×2160 / 59.94 fps / 160 Mbps |

一个 15 段的时间线要 1 分多钟，段数显然不是变量 —— 变量是那唯一一段变速。
按 4.5 GB / 63 秒 ≈ 72 MB/s 的 ProRes 码率反推，编码时间必然在分钟级。
随后用同一个 ffmpeg、同一段源实测，坐实了这一点（见下表）。

## 2. 实测（RTX 4060 Laptop / 32 线程 / 同一源文件）

单帧成本用固定 300 帧切片测，避免整段太慢；整段用真实参数复测一次。

| 做法 | 300 帧耗时 | 每帧 | 换算 1903 帧 |
| --- | --- | --- | --- |
| 4K + `prores_ks`（旧行为） | 13.0 s | 43.5 ms | **82 s** / 4.5 GB |
| 1080p + `prores_ks` | 5.7 s | 19.1 ms | 36 s / 0.6 GB |
| 1080p + `prores_aw`（新行为） | 4.4 s | 14.7 ms | **34 s** / 1.4 GB |
| 1080p + `prores_aw` + CUDA 解码 | 3.3 s | 11.1 ms | 21 s（未采用，见 §4） |

整段复测（1903 帧，`retime.bake` 生产路径）：**34.1 秒 / 1,387,154,905 B**，
产物 1920×1080 / 30 fps / `prores_aw` Standard / `yuv422p10le`。

顺带测到的几件事（都影响结论，所以记下来）：

- **不是编码器慢**：`prores_aw` 编 1080p 是 292 fps，`prores_ks` 只有 104 fps。
  两者都是 10bit 4:2:2 Standard，`prores_aw` 码率更高（237 vs 174 Mbps），
  质量只有更好。
- **瓶颈是解码**：这段 4K H.264 软解 174 fps。1903 帧输出要吃 5526 帧源
  （92 秒 × 59.94），5526 / 174 ≈ 32 秒 —— 和实测 34 秒对上了。
- **d3d11va 不解渴**：纯解码 3.67 s vs 软解 3.45 s。硬件解码快，但 4K 帧
  下载回内存的开销把收益吃掉了。
- **CUDA 全程留在显存**才有效（`scale_cuda` + `hwdownload`），但见 §4。

## 3. 改了什么

`colorpass/retime.py`

1. `video_filter(speed, size)`：滤镜链里加
   `scale=w='min(iw,W)':h='min(ih,H)':force_original_aspect_ratio=decrease`。
   - **只缩不放**：1080p 源不会被放大到 4K 再编；
   - `fps` 在 `scale` 之前：1.45 倍速时源帧比输出帧多，先抽帧再缩放，少缩三成。
2. 编码器按 `prores_aw` → `prores_ks` 顺序试，第一次成功的记在进程内，后续段直接用。
3. `cache_path(..., size)`：把画布写进缓存键。不写的话升级后仍会命中 4K 老缓存。

`colorpass/send.py`

4. 预渲染从「读草稿之后、连达芬奇之前」挪到「拿到工程画布之后」——
   画布（`timelineResolutionWidth/Height`）只有连上工程才知道。
5. 新增 `timings`：`read / snapshot / bake / media / place / finish / total`，
   报告里能直接看到每一段花了多少秒；命令行末尾再念一行「耗时 x.x 秒（大头在前）」。
   失败路径也会带上（`_fail` 里补），否则「为什么这么慢还失败了」仍然没数据。
6. `baked[].sec / enc / bytes`：每段预渲染的真实耗时和编码器。

## 4. 没做的事（写清楚原因）

- **CUDA 解码**：能把 34 秒压到 21 秒，但只对 NVIDIA 有效；滤镜链要变成
  `scale_cuda` + `hwdownload`，10bit 源（p010）还得单独保证不变 8bit。
  一个「看起来能跑但悄悄丢了色深」的路径，比慢 13 秒更糟。要做就得先有一份
  10bit 源做逐帧比对，现在没有。
- **把一段切片并行编**：帧边界和 `setpts` 的舍入会漂，而这条链的全部价值就是
  「帧位与剪映严格对齐」。不值得。
- **不 bake**（退回 1x 摆放）：快，但加速段会缺尾巴、慢放段会串帧 ——
  那是把「慢」换成「错」。

## 5. 下次说「还是慢」时看哪里

```text
%LOCALAPPDATA%\ColorPass\runs\<草稿ID>\send.json  →  timings
```

- `bake` 大：变速段多 / 源是 4K；先看 `baked[].cached` 是否 false（第一次必编）。
- `read` 大（>8 秒）：剪映内存扫描；草稿刚被编辑过又没有本地明文副本时会这样。
- `media` 大：素材没进过媒体池，第一次导入（含 Resolve 自己分析素材）。
- `place` 大：段数特别多（每段一次 `AppendToTimeline` + 一次 `AddMarker`）。

`python -m colorpass.cli clean --draft-id <ID>` 可以随时清掉预渲染缓存
（可再生产物，原素材和草稿都不受影响）。

## 6. 磁盘：一次送入会多占多少

会多一份，但只针对「需要重算画面的段」，不是整片复制。导入达芬奇是**按路径
引用**，媒体池里不会多一份视频文件。

| 池 | 内容 | 体积 | 什么时候有 |
|---|---|---|---|
| `retime/<草稿ID>/` | 变速段重采样成的 ProRes 422 10bit | **18~22 MB/s，一分钟 1.1~1.3 GB** | 草稿里有变速段才有 |
| `photos/<草稿ID>/` | 图片段转成的等长 H.264 视频 | 一张图约 1 MB | 有图片段才有 |
| `luts/<草稿ID>/` | 取回时导出的 cube 工作副本 | 约 12~14 MB | 写回剪映之后 |
| `runs/<草稿ID>/` | 报告 + 写回用的底稿快照 | 几百 KB | 每次送入 |

实测（2026-11-23，63 秒的 4K 变速段）：这一段就 1.39 GB。

三条边界：

1. **会自动收。** 每次送入/写回成功后静默跑一次回收：剪映里已删除的草稿、
   超过 60 天没动过的、同池超过 8 份的、总量超 1200 MB 的，都会被清掉
   （`gc.auto()`，见 `colorpass/gc.py` 开头）。
2. **同一份草稿内也会收。** 这是 0.6.3 补的洞：缓存文件名带「段 + 速度 +
   源区间」，改一次倍速就多一个文件，而目录级回收把活动草稿整个保护起来
   （写回还要读它的快照），不单独处理就会越攒越多。现在送入成功后按
   「本次实际用到的产物」反删，只留这条时间线正在用的那几个。
3. **别随手清。** 这些中转素材同时是达芬奇时间线正在引用的**正片素材**，
   删掉之后那条旧时间线会显示媒体离线（重新送入即可再生成，但当前调色会丢）。
   要清就先在达芬奇里做完、渲染完。

想知道现在占了多少：`ColorPass.exe doctor` 里的 `cache` 段，或者面板
「诊断」窗口里搜 `cache`。

省空间的唯一有效手段是中转码率：同样 1080p 30fps、同样 10bit 4:2:2，
`prores_aw` 的 Proxy 档只有 Standard 的 32%（0.38 GB/分钟 vs 1.18），编码
速度一样（都是解码受限）。代价是画面细节——只用来取 LUT 没问题，要在达芬奇
里直接渲染成片就得再想想。
